# Оптимизация программы

## Ключевые изменения

### test1

Базовый вариант.

- Файлы читались построчно.
- Каждая строка разбиралась через `std::stringstream`.
- Парсинг, фильтрация, слияние и сортировка выполнялись отдельными этапами.

### test2

`std::stringstream` заменён на прямой поиск разделителей через `std::string::find()`.

Это убрало создание потокового объекта и работу через `streambuf` для каждой строки CSV.

### test3

Парсинг, фильтрация и слияние объединены в один проход.

Строки вне диапазона дат отбрасываются до создания `Row` и до преобразования `float64`. Исчезли промежуточные `rows` и `filteredRows`.

### test4

`std::stod(line.substr(...))` заменён на `std::from_chars()`.

Число преобразуется прямо из исходного диапазона символов без создания временного `std::string`.

### test5

Для временной работы с именем и датой использован `std::string_view`.

Это уменьшило количество копирований строк в горячем цикле.

### test6

Проверен `std::map` вместо связки `unordered_map + vector + sort`.

Результат оказался медленнее из-за древовидной структуры, сравнений строк и разрозненного размещения узлов в памяти.

### test7

Проверена фиксированная таблица сумм.

Само накопление стало очень дешёвым, но выигрыш частично потерялся из-за двух `std::lower_bound()` для поиска `nameId` и `dateId`.

### test8

Поиск даты через `lower_bound` заменён прямым вычислением индекса дня.

Имя стало переводиться в `nameId` через `unordered_map<string_view, id>`.

### test9

`std::getline()` и `std::string::find()` заменены на чтение файла целиком в `std::vector<char>` и последовательный разбор CSV через `const char*`.

Это дало самый заметный прирост на позднем этапе однопоточной оптимизации.

### test10

Первая универсальная версия.

Она сохраняет разбор CSV через указатели, но больше не зависит от заранее известных имён и фиксированного набора дат.

- Имена обнаруживаются динамически.
- Поддерживается список входных файлов.
- Настраиваются разделитель CSV, разделитель даты и десятичный разделитель.
- Формат даты задаётся как `YMD`, `DMY` или `MDY`.
- Дата внутри программы преобразуется в единое число `YYYYMMDD`.
- Группа `name + date` кодируется компактным числовым ключом `uint64_t`.
- Основной pipeline собран в `processFiles()`.

Универсальность немного увеличила стоимость обработки даты по сравнению со специализированным вариантом.

### test11

Проверен специализированный разбор даты для наших тестовых файлов с форматом `YYYY-MM-DD`.

Вместо прохода по символам и определения порядка `Y/M/D` цифры читаются напрямую по известным позициям:

- `date[0..3]` — год;
- `date[5..6]` — месяц;
- `date[8..9]` — день.

Так как дата разбирается для каждой входной строки ещё до фильтрации, даже небольшое уменьшение стоимости одного вызова дало заметный общий прирост.

### test12

Проверена обработка файла блоками во время чтения.

Вместо чтения всего файла целиком в один большой `vector<char>` используется буфер размером 4 MB:

1. читается очередной блок;
2. все полные строки внутри него сразу разбираются;
3. незаконченный хвост строки переносится в начало буфера;
4. после этого читается следующий блок.

Это одновременно уменьшило потребление памяти и ускорило обработку за счёт работы с меньшим повторно используемым буфером.

### test13

Проверена параллельная обработка двух файлов двумя потоками.

- `data1.csv` обрабатывается первым потоком;
- `data2.csv` обрабатывается вторым потоком;
- каждый поток использует алгоритм `test12`;
- у каждого потока собственные `names`, `nameIds` и `sums`;
- общих `unordered_map` в горячем цикле нет, поэтому `mutex` не требуется;
- после `join()` два небольших отсортированных результата объединяются линейным merge.

Это дало самый большой прирост после перехода к указательному парсеру.

### test14

Финальная универсальная версия на основе `test13`.

Она объединяет универсальность `test10` и быстрые алгоритмы `test11-test13`.

- Поддерживается произвольный список входных файлов.
- Каждый файл обрабатывается отдельным потоком.
- Каждый поток читает свой файл блоками по 4 MB.
- Поддерживаются `YMD`, `DMY` и `MDY`.
- Позиции года, месяца и дня определяются один раз до начала обработки.
- В горячем цикле дата читается напрямую по заранее вычисленным позициям.
- Поддерживаются настраиваемые CSV-разделитель, разделитель даты и десятичный разделитель.
- Имена определяются динамически.
- Частичные результаты потоков объединяются после завершения обработки файлов.

Таким образом универсальность больше не требует возвращаться к медленному посимвольному разбору формата даты для каждой строки.

## Как работает итоговый test14

В `main()` задаются:

- список входных файлов;
- разделитель колонок CSV;
- разделитель даты;
- десятичный разделитель `float64`;
- формат даты `YMD`, `DMY` или `MDY`;
- начальная дата;
- конечная дата.

Перед началом обработки функция `getDatePositions()` один раз определяет позиции года, месяца и дня.

Например для `DMY` и даты `07.11.2026`:

- день начинается с позиции 0;
- месяц — с позиции 3;
- год — с позиции 6.

Дальше общий pipeline выглядит так:

1. Для каждого входного файла создаётся отдельный поток.
2. Каждый поток открывает только свой файл.
3. Файл читается блоками по 4 MB.
4. Полные строки блока сразу разбираются через `const char*`.
5. Незаконченная строка на границе блоков переносится в начало буфера через `std::memmove()`.
6. Дата напрямую преобразуется в `YYYYMMDD` по заранее известным позициям.
7. Строки вне диапазона дат сразу отбрасываются.
8. Имя временно представляется через `std::string_view` без копирования.
9. Каждому новому имени назначается числовой `nameId`.
10. `float64` преобразуется непосредственно из диапазона `char`.
11. `nameId` и дата упаковываются в один `uint64_t`.
12. Сумма накапливается в локальном `unordered_map` потока.
13. После завершения файла поток создаёт небольшой отсортированный `vector<Row>`.
14. После `join()` частичные результаты файлов объединяются линейным merge.
15. Готовый результат выводится в консоль и сохраняется в `data/merged.csv`.

Вывод и сохранение выполняются после замера времени и поэтому не входят в `Processing`.

## Основные выводы

Переход от `test10` к специализированному разбору даты в `test11` показал, что оптимизация маленькой функции имеет смысл, если она вызывается миллионы раз.

Переход от `test11` к блочному чтению в `test12` показал, что изменение архитектуры ввода может дать больший эффект, чем локальная замена STL-конструкций.

Переход от `test12` к двум независимым потокам в `test13` уменьшил лучшее время с `54.367 ms` до `30.999 ms`.

При сравнении исходного `test1 -O2` и лучшего специализированного результата `test13 -O3`:

`976.788 / 30.999 ≈ 31.5`

То есть специализированный вариант оказался примерно в **31.5 раза быстрее** первоначальной реализации.

При сравнении исходного `test1 -O2` и финального универсального `test14 -O3`:

`976.788 / 34.069 ≈ 28.7`

То есть финальная универсальная версия оказалась примерно в **28.7 раза быстрее** первоначальной реализации, сохранив поддержку произвольного списка файлов, разделителей и форматов даты.

Главный вывод всей последовательности тестов: наибольший эффект дали не мелкие синтаксические изменения, а уменьшение числа проходов по данным, отказ от лишних строковых объектов, последовательный разбор памяти, блочное чтение и параллельная обработка независимых файлов.
