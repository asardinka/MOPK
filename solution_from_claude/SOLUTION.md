## 2. Сборка, запуск, проверка

```powershell
# ucrt64 лучше ставить В НАЧАЛО PATH (см. примечание ниже)
$Env:PATH = "C:\msys64\ucrt64\bin;" + $Env:PATH

g++ -std=c++17 -O2 solution_from_claude/solution.cpp -o build/solution.exe
build/solution.exe                                  # параметры по умолчанию = test14

# проверка: сохранить результат в файл и сравнить побайтово с эталоном
build/solution.exe --quiet --out build/out.csv > $null
fc.exe /b build\out.csv data\merged.csv
```

Результат (CSV) печатается в **stdout**, сведения о железе и время — в **stderr**, поэтому `solution.exe > file.csv` даёт чистый CSV. В PowerShell для сравнения удобнее `--out`: оператор `>` в PowerShell перекодирует текст.

Параметры (по умолчанию — как в test14):

```text
solution [options] [file.csv ...]        без файлов: data/data1.csv data/data2.csv
  --from DATE / --to DATE    диапазон дат (включительно), по умолчанию 2026-11-01 .. 2026-11-10
  --format YMD|DMY|MDY       порядок полей даты
  --sep C                    разделитель CSV (',' ';' tab)
  --date-sep C               разделитель даты ('-' '.' '/')
  --dec C                    десятичный разделитель ('.' или ',')
  --out FILE                 дополнительно сохранить результат в файл
  --threads N                фиксированное число потоков (по умолчанию подбирается измерением)
  --chunk-kb N               размер чанка (по умолчанию из размера L2)
  --mem-mb N                 бюджет памяти (по умолчанию из свободной RAM)
  --quiet                    не печатать сведения о железе
```

Пример для другого формата: `build/solution.exe --format DMY --date-sep . --sep ";" --dec , --from 01.11.2026 --to 10.11.2026 a.csv b.csv c.csv`

В stderr программа показывает, что она узнала о железе и какой план выбрала:


**Примечание про PATH.** Если `C:\msys64\ucrt64\bin` стоит в PATH *после* Git (`$Env:PATH += ...`), Windows может загрузить чужую `libstdc++-6.dll` из Git for Windows, и программа, собранная MSYS2, падает (у меня так падал test14). Надёжнее ставить ucrt64 в начало PATH или собирать с `-static`: по скорости статическая сборка не отличается (21.9 против 22.5 мс полного времени — в пределах шума), но от DLL не зависит.

## 4. Подстройка под страницы и кэш

Это то, о чём вы спрашивали отдельно. Короткий ответ: **данные надо подавать процессору кусками, которые помещаются в его L2, читать их с границ страниц в один и тот же выровненный буфер, а горячие структуры раскладывать по кэш-линиям**. А вот отображать файл в память (mmap), хотя это кажется очевидным ходом «под страницы», на Windows оказалось заметно медленнее — ниже почему.

### 4.1. Что программа узнаёт о железе

| Что | Откуда (Windows / Linux) | Для чего |
|---|---|---|
| Размер страницы, гранулярность выделения | `GetSystemInfo` / `sysconf(_SC_PAGESIZE)` | выравнивание смещений чтения и буферов |
| L1d, L2, L3, сколько потоков делят L2 | `GetLogicalProcessorInformationEx` / `/sys/devices/system/cpu/cpu0/cache` | размер чанка |
| Физические ядра, доступные процессу CPU | то же + affinity mask / `sched_getaffinity` | верхняя граница числа потоков |
| Свободная RAM | `GlobalMemoryStatusEx` / `/proc/meminfo` | бюджет памяти |

На гибридных процессорах (P- и E-ядра с разным L2) берётся самый маленький L2 на поток.

### 4.2. Размер чанка = половина L2 на один аппаратный поток

```text
chunk = L2 / (потоков на L2) / 2 = 1024 KB / 2 / 2 = 256 KB   (на этой машине)
```

Поток читает чанк системным вызовом в свой буфер. Ядро ОС копирует данные из файлового кэша — и после копирования они уже лежат в L2 этого ядра. Если чанк помещается в L2, разбор идёт из L2 (≈14 тактов на обращение), а не из L3 или памяти. Вторая половина L2 остаётся под таблицы, стек и код. SMT-«близнецы» делят один L2, поэтому делим на 2.

Замер (только чтение, без разбора, 16 потоков), мс:

| Чанк | 64 KB | 128 KB | 256 KB | 512 KB | 1 MB | 4 MB (как в test14) |
|---|---:|---:|---:|---:|---:|---:|
| Время | 23.0 | 19.4 | 18.9 | 18.8 | 22.1 | 30.7 |

Слишком маленький чанк — много системных вызовов; слишком большой — данные вытесняются из L2 до разбора, а чанков мало для равномерной загрузки потоков. Оптимум 256–512 KB совпадает с формулой. На процессоре с L2 = 256 KB получится 64 KB и т. д.

### 4.3. Выравнивание по страницам

- Размер чанка кратен **гранулярности выделения** (64 KB на Windows, страница на Linux), значит каждое чтение начинается с границы страницы: ОС копирует целые страницы кэша.
- Буфер потока выделяется **выровненным на страницу** и **переиспользуется** для всех чанков: его страницы один раз «прогреваются» (page fault при первом касании) и дальше всё время остаются в L2 и в TLB. В test14 на каждый файл выделялось 8 MB, которые целиком не помещаются ни в L2, ни в TLB первого уровня.
- Чтобы захватить конец последней строки чанка, читается ещё **одна страница** сверху (4 KB). Если строка длиннее — редкий медленный путь дочитывает.

### 4.4. Почему не отображение файла в память (mmap)

Идея «разбирать прямо из страниц файлового кэша, без копирования» выглядит как идеальная подстройка под страницы. Замеры (полный разбор), мс:

| Способ | 1 поток | 16 потоков |
|---|---:|---:|
| ReadFile в L2-буфер | 59.2 | 20.4 |
| MapViewOfFile, разбор из отображения | 96.1 | 30.2 |
| MapViewOfFile + PrefetchVirtualMemory | 103.7 | 41.1 |

Причины:
1. **Page fault на каждые 4 KB.** Даже просто коснуться одного байта на каждой странице двух файлов — 38 мс на одном потоке: ~43 000 soft fault по ~0.9 мкс. Windows не подгружает соседние страницы отображения пачкой.
2. **Page fault сериализуются** на блокировке рабочего набора процесса, поэтому с ростом числа потоков mmap масштабируется хуже.
3. **Данные не в L2.** При ReadFile ядро само копирует страницу в буфер, и она оказывается в L2. При mmap разбор идёт по страницам в DRAM.
4. `PrefetchVirtualMemory` только добавляет системных вызовов.

### 4.5. Кэш-линии

- **Ячейка группы = ровно одна кэш-линия.** Ключ (8 байт) + 7 сумм `double` (56 байт) = 64 байта, массив выровнен на 64. Обновление группы затрагивает одну линию памяти — и ключ для сравнения, и все 7 сумм. Если значений не 7, шаг ячейки округляется вверх до кратного 64.
- **Нет false sharing.** У каждого потока свои таблицы и буфер (`alignas(64)`); счётчики чанков каждого файла лежат на отдельных кэш-линиях. Потоки не пишут в общие линии в горячем цикле.
- **Таблица имён** помещается в L1 (50 имён → 128 слотов по 24 байта).

### 4.6. Что сознательно не использовано

- **Large pages (2 MB)** — на Windows требуют привилегии `SeLockMemoryPrivilege` (по умолчанию её нет) и применимы только к анонимной памяти, а не к файловому кэшу. Наши буферы и так малы и живут в TLB.
- **`FILE_FLAG_NO_BUFFERING`** (чтение с диска в обход кэша ОС): 82–241 мс против 19 мс — диск медленнее, чем файловый кэш в памяти.
- **Программная предвыборка** (`_mm_prefetch`) не нужна: доступ строго последовательный, аппаратный prefetcher справляется.

## 5. Параллелизм

### 5.1. Чанки вместо «поток на файл»

В test14 потоков столько, сколько файлов: на 2 файлах занято 2 ядра из 16, на 100 файлах — 100 потоков по 8 MB. Здесь все файлы режутся на чанки, и **любой поток может обработать любой чанк**. Работа распределяется динамически через атомарный счётчик — если данные неравномерны (например, файл отсортирован по дате и все подходящие строки в одном месте), быстрые потоки просто возьмут больше чанков.

**Как не разрезать строку на границе чанков.** Правило: *чанк `[a, b)` обрабатывает строки, которые начинаются сразу после `'\n'`, стоящего в позиции `p ∈ [a, b)`*. Каждая строка начинается сразу после ровно одного `'\n'`, значит, достаётся ровно одному чанку. Заголовок файла (строка с позиции 0) не стоит после `'\n'` и пропускается сам собой. Никакого обмена «хвостами» между потоками не нужно.

```text
файл:  ...xxx\nAAAA\nBBBBBB|BB\nCCC\n...     | — граница чанков a/b
чанк 1: строки после '\n' с позицией < b: AAAA, BBBBBBBB (дочитывается за границу)
чанк 2: первый '\n' в чанке 2 — после BB, значит, начинает с CCC
```

### 5.2. Свой счётчик чанков у каждого файла

Сначала чанки раздавались по порядку: весь первый файл, потом второй. Замер показал, что ReadFile упирается в блокировки **файлового кэша ОС, а они — на каждый файл**. Когда у каждого файла свой счётчик, а поток `i` начинает с файла `i % F` (и помогает другим, когда его файл закончился), потоки распределены по файлам, и блокировки не мешают друг другу:

| 16 потоков | порядок «файл за файлом» | свой счётчик у файла |
|---|---:|---:|
| Processing, мс | 18.45 | 15.63 |

Внутри файла чанки по-прежнему читаются по возрастанию смещения — read-ahead ОС работает, а для HDD чтение остаётся почти последовательным.

### 5.3. Регулятор числа потоков: не «все ядра», а столько, сколько даёт выигрыш

Замер (-O2, медианы), 2 файла:

| Потоков | 4 | 6 | 8 | 10 | 12 | 16 | 32 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Processing, мс | 18.7 | 15.5 | 15.6 | 16.1 | 17.0 | 16.6 | 19.6 |
| Полное время процесса, мс | 25.6 | 22.1 | 21.3 | 22.4 | 23.8 | 23.5 | 27.0 |

После 6–8 потоков станет только хуже: чтение из файлового кэша упирается в память и блокировки ядра ОС, и лишние потоки просто мешают друг другу. «Загрузить все 32 потока» — на 25% медленнее и тратит в 4 раза больше CPU.

Но **оптимум нельзя вычислить по характеристикам железа** — он зависит ещё и от данных. На 20 файлах (те же два файла, переданные 10 раз, 1.7 GB) блокировки распределяются по 20 файлам, и оптимум сдвигается: 8 потоков — 135–155 мс, 16 потоков — 83–105 мс (длинные прогоны на ноутбуке шумные, поэтому диапазоны из двух серий).

Поэтому число потоков **подбирается измерением** (hill climbing — так же подбирает число потоков пул потоков .NET):
1. старт — с половины физических ядер (задача, упирающаяся в память, на клиентских машинах редко масштабируется дальше);
2. каждые ~1.5 мс главный поток считает скорость (байт/мс);
3. если работы осталось хотя бы на ~20 таких окон, пробует удвоить число потоков; удвоение оставляется, только если скорость выросла ≥ 25%;
4. если прироста нет — лишние потоки доделывают свой чанк и выходят.

Итог: на 2 файлах регулятор остаётся на 8 потоках без проб (работы слишком мало, чтобы проба окупилась); на 1.7 GB сам доходит до 16 потоков (в журнале, например: `8 thr 12.2 GB/s -> 16 thr 16.6 GB/s -> kept 16 threads`). Потоки создаются только по мере надобности, так что на маленьком файле лишние потоки не создаются вовсе. Верхняя граница — число **физических** ядер: SMT-«близнецы» делят L2 и шину памяти, а задача упирается в память.

## 6. Разбор строки

### 6.1. Строки перечисляются по битовой маске

Каждые 64 байта буфера превращаются в одно 64-битное слово: SSE2 сравнивает 4 × 16 байт с `'\n'`, `movemask` собирает биты. Начала строк достаются из слова командой `tzcnt` (номер младшего единичного бита) и `x &= x - 1` (сбросить его). **Конец строки искать не нужно**: следующая строка известна из маски, не дожидаясь разбора текущей.

Отбрасываемая строка: 10.7 → 8.9 нс (весь файл без попаданий в диапазон: 10.6 → 8.9 мс).

### 6.2. Разделители одной маской, дата — по позициям

На первые 32 байта строки строятся две маски: где разделители и где `'\n'`. Два младших бита маски разделителей — конец `id` и конец имени, третий должен стоять ровно через 10 символов (дата фиксированной ширины). Это ~15 команд без циклов вместо двух посимвольных циклов с непредсказуемым выходом. Длинные `id`/имена (не влезли в 32 байта) и нестандартные даты уходят в медленный универсальный путь.

Дата читается по позициям, вычисленным один раз из формата (как в test14), и сравнивается с диапазоном **одним** беззнаковым сравнением: `key - start > span`. **~90% строк на этом заканчиваются**: имя, хеш-таблицы и 7 чисел для них не трогаются. Для строк в диапазоне дата дополнительно проверяется (цифры, разделители, месяц 1–12, день 1–31) — мусор не может случайно попасть в результат.

### 6.3. Числа: быстрый путь с тем же результатом, что from_chars

Все цифры числа собираются в одно целое `m` (без учёта точки), результат — `m / 10^k`. Если `m ≤ 2^53` и `k ≤ 22`, то и `m`, и `10^k` представимы в `double` точно, а деление по IEEE 754 округляется корректно — значит, результат **бит в бит совпадает с `from_chars`** (это «быстрый путь Клингера»). Экспонента (`5.12345e-05` — в данных их ~700 на файл), слишком длинные числа и прочее — через `from_chars`. Для десятичной запятой копия поля с заменой `,` → `.` — без накопления ошибки `factor *= 0.1`, как в test14.

Изолированный замер, нс на одно число: `from_chars` — 10.3, быстрый путь — **6.1**.

### 6.4. Хеш-таблицы

- **Имя → nameId**: open addressing с линейным пробированием. В слоте хранятся первые 8 байт имени — для имён до 8 байт (большинство) сравнение сводится к сравнению двух чисел, без `memcmp`.
- **(nameId, дата) → суммы**: ключ `nameId << 32 | YYYYMMDD`, хеш Фибоначчи, ячейка 64 байта (4.5).
- **Сортировка**: имена сортируются один раз (50 строк), потом группы — по целому ключу `rank(имя) << 32 | дата`. Строки при сортировке не сравниваются.

## 7. Память и слабое железо

### 7.1. Память

| Сценарий | Peak private | Peak working set |
|---|---:|---:|
| test14, 2 файла | 17.3 MB | 21.4 MB |
| solution, 2 файла (8 потоков) | **4.2 MB** | 8.1 MB |
| solution, 1 поток | **1.5 MB** | 5.5 MB |
| solution, 20 файлов, 1.7 GB | 7.2 MB | 11.0 MB |

Память **не зависит от размера файлов**: на поток — буфер чанка (~260 KB) и таблицы. test14 на 20 файлах запустил бы 20 потоков по 8 MB.

Бюджет памяти — четверть свободной RAM (не больше 2 GB) или `--mem-mb`:
- число потоков ограничивается так, чтобы буферы занимали не больше половины бюджета;
- при очень маленьком бюджете уменьшается размер чанка;
- если групп очень много (миллионы пар имя×дата), локальная таблица потока, превысившая свою долю бюджета, **сливается в общую** и очищается. Проверено: 100 000 имён, `--mem-mb 4` → программа сама снизила число потоков до 3, сделала 11–22 слияния, результат точный.

### 7.2. Слабое железо

- **Только SSE2** — он есть у любого x86-64, программа запустится на любом 64-битном процессоре. `-march=native` (AVX2 и т. д.) проверен — выигрыша нет, узкое место не в ширине векторов. Для не-x86 (ARM) есть простые версии без SIMD.
- **Однопоточная скорость важна сама по себе** — на 1–2 ядрах параллелизм не спасёт:

| Потоков (`--threads`) | 1 | 2 | 4 | авто (8) |
|---|---:|---:|---:|---:|
| Processing, мс | 47.0 | 25.4 | 16.7 | 12.6 |

  Один поток solution (47 мс) быстрее, чем test14 на двух (58 мс).
- Для маленьких данных не создаются лишние потоки (минимум ~4 чанка на поток и регулятор).

## 9. Как измерялось

- **Варианты запускались вперемешку** (A, B, C, A, B, C, …), по 15–20 раз, бралась медиана. Ноутбук под нагрузкой меняет частоту, и серия «сначала все A, потом все B» даёт разброс больше самой разницы.
- **Два таймера**: внутренний `Processing` (как в test14) и полное время процесса снаружи. Разница — ~6–8 мс (создание процесса, загрузка DLL, выход). Пример с гибридом (раздел 8) показывает, почему нужны оба.
- **Парсер отдельно**: файл целиком загружается в память, и `parse()` меряется без чтения — так видно, сколько стоит сам разбор строки.
- Длинные прогоны (1.7 GB) на ноутбуке шумные (разброс 80–140 мс из-за нагрева), поэтому по ним сделаны только качественные выводы.
- Все временные программы, бенчмарки и копии данных были в отдельной временной папке и удалены.

## 11. Универсальность и ограничения

Поддерживается:
- любое число файлов любого размера (память от размера не зависит);
- форматы даты YMD / DMY / MDY, любой разделитель даты, даты без ведущих нулей (универсальный медленный путь);
- любой разделитель CSV и десятичный разделитель;
- **любое число столбцов значений** — берётся из заголовка первого файла (в test14 было жёстко 7); заголовок вывода повторяет имена столбцов входа;
- CRLF и LF, отсутствие `\n` в конце, пустые строки, некорректные строки (пропускаются), пустые значения (= 0).

Ограничения (как и в test14):
- порядок столбцов фиксирован: `id, имя, дата, значения…`; первая строка каждого файла — заголовок;
- кавычки CSV (`"a,b"`) не поддерживаются;
- пробелы вокруг чисел не обрезаются;
- **ветка для Linux/POSIX написана** (`pread`, `posix_fadvise`, `sysconf`, `/sys/.../cache`, `/proc/meminfo`), **но не проверена**: в этой среде нет ни WSL-дистрибутива, ни POSIX-компилятора. Всё проверенное — на Windows.

## 12. make_csv_opt.cpp

```powershell
g++ -std=c++17 -O2 solution_from_claude/make_csv_opt.cpp -o build/make_csv_opt.exe
build/make_csv_opt.exe                         # как make_csv: data/data1.csv, data/data2.csv по 1 000 000 строк
build/make_csv_opt.exe --rows 5000000 --files 4 --dir data --seed 42 --threads 8
```

Формат строк тот же: тот же заголовок, те же 50 имён, те же 103 даты, 7 значений из [0, 1) ровно в том виде, как печатает `std::cout << double`, CRLF на Windows (как у текстового `ofstream`). Проверено регулярным выражением на каждой строке: у новых и старых файлов одинаковая статистика — 50 имён, 103 даты, среднее 0.500, ~650 чисел в экспоненциальной записи на миллион строк.

Полное время процесса, 2 × 1 000 000 строк (одна серия, запуски вперемешку, медиана):

| | Без оптимизации | -O2 |
|---|---:|---:|
| make_csv.cpp | 7245 мс | 6349 мс |
| **make_csv_opt.cpp** | **109 мс** | **77 мс** |
| Ускорение | 66× | 82× |

| Потоков (-O2) | 1 | 2 | 4 | 8 (авто) | 16 |
|---|---:|---:|---:|---:|---:|
| мс | 199 | 143 | 92 | 77 | 73 |

Память: 6.8 MB (8 потоков), 2.7 MB (1 поток). Исходный `make_csv` — 1.1 MB: он пишет потоком через буфер 64 KB, но и работает в 80 раз дольше.

Что ускорило:
1. **`ostream << double` → целочисленная арифметика.** Значение генерируется как `x = r / 2^53`, где `r` — 53 случайных бита. Шесть значащих цифр — это `q = round(r · 10^k / 2^53)`: одно 128-битное умножение и сдвиг; остаток сдвига даёт точное округление «к ближайшему, при равенстве — к чётному», как у `printf`. Цифры выписываются в буфер напрямую, без локали и виртуальных вызовов потока. Редкие числа < 10⁻⁴ (экспоненциальная запись) — через `std::to_chars`.
2. **xoshiro256\*\*** вместо `mt19937` + `uniform_real_distribution`; имя и дата выбираются умножением (метод Лемира) вместо деления.
3. **id увеличивается прямо в ASCII-буфере** (меняется обычно одна последняя цифра); имя и дата копируются одной `memcpy` фиксированной длины из заранее подготовленной таблицы.
4. **Конвейер «генераторы → писатель»**: потоки генерируют блоки по 4096 строк, главный поток пишет их в файл строго по порядку. Буферов T + 2 — память ограничена, сколько бы строк ни генерировалось. Буфер берётся до номера блока, поэтому самый ранний незаписанный блок всегда у потока, у которого уже есть буфер, — взаимная блокировка невозможна. Сама генерация на 16 потоках занимает ~23 мс, остальное — запись 178 MB в файловый кэш (~45 мс; параллельная запись не помогает, см. раздел 8). Поэтому генераторов по умолчанию — половина физических ядер: больше писатель всё равно не успевает забирать.
   - Первая версия брала блоки по 16 384 строки и все ядра — 48 MB памяти. Замер показал, что размер блока от 2K до 16K строк на скорость не влияет (узкое место — запись), а 8 потоков не медленнее 16. Итог — 6.8 MB при той же скорости.
5. **Воспроизводимость**: seed блока зависит только от `(seed, файл, блок)`, поэтому одинаковый `--seed` даёт побайтово одинаковые файлы при любом числе потоков (проверено: 1, 3, 16).
